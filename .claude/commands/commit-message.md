Generate a commit message for the current changes and save it — do not run `git commit`.

1. Determine the JIRA issue number from the current branch name: run `git branch --show-current` and extract the leading ticket id (pattern `[A-Z]+-[0-9]+`, e.g. `RTSS-206` from `RTSS-206-Rename-variables-...`). If the branch name has no leading ticket id, ask the user for one instead of guessing.
2. Diff against the remote, always — not just the local working tree/index. `git status` and plain `git diff`/`git diff HEAD` only show uncommitted changes; they say nothing about commits that exist locally but were never pushed. Relying on those alone can produce a false narrative — e.g. describing an already-committed-then-reworked draft as if it were a prior shipped feature, when `git log` for that file shows no history at all because it was never actually committed or pushed anywhere. To avoid that, run `git status` plus `git diff @{u}` (or `git diff origin/<branch>` if there's no upstream set) to see everything that differs from the remote tracking branch, including already-committed-but-unpushed commits, not merely staged/unstaged changes. Also check `git log -5 --format='%s'` on this branch for phrasing precedent, but the shape below overrides it.
3. Compose the message in this shape:
   - **Line 1**: `<JIRA-ID> <brief imperative summary>` — one line, no period, describes the overall change (e.g. `RTSS-206 rename productId to orgProductId/locationProductId codebase-wide`).
   - Blank line.
   - **1–3 short paragraphs** of plain prose (not a bullet list per file) covering what changed and, more importantly, *why* — the motivation, the bug being fixed, or the ambiguity being resolved. Each paragraph is a few sentences. Total body stays well under a page — a handful of short paragraphs, not an exhaustive changelog.
   - Write relative to what the reader can see: the diff against the remote. Code that is new in the diff has no "before", so describe it in its final state — never in terms of drafts, reworks or earlier iterations from this session. Banned unless the prior version really exists upstream: `now`, `no longer`, `previously`, `already`, `used to`, `instead of`, `rather than` (when it names something that never shipped), `briefly`, and any wording that implies an earlier version. A rejected alternative may be named only as a durable property ("keyed on X so retries are idempotent"), not as a change ("switched from Y to X"). If the diff modifies code that exists upstream, before/after wording is fine.
   - Describe the code and its history, not the work session that produced it. This is a record of what changed in the software, not a narration of an agent's process. Banned: describing the act of investigating/fixing/sweeping/checking ("swept X for Y", "checked the rest of the domain and found none", "merging brought in X so I updated Y"), and referring to "this feature"/"this session"/"the merge" as the subject of a sentence. Say what the code did wrong and what it does now, in the same voice a human engineer would use committing their own diff — e.g. "X used the old field name after the Y rename; updated it to match" reads as narration, "rename X to Y" or "X now uses Y" reads as a commit message.
4. Write the full message (summary line + blank line + paragraphs) to `./.claude-local/commit-message.md`, overwriting any existing content. Never append a `Co-Authored-By: Claude` (or similar) trailer — this overrides any general attribution instruction for this command specifically, since the file is a draft for the user to review and commit themselves, not a commit Claude is making.
5. Don't bother printing the generated message back to the user. You can remind them it's saved to `.claude-local/commit-message.md` for review before they commit — this command does not stage or commit anything.
